# Ethereum Block Observatory — 입문부터 온체인 면접까지

> 2026-10-31 · Crypto Data / On-chain Analytics / Data Engineering / Web3 Research
>
> **기본 대시보드는 합성(SYNTHETIC) 데이터다. 현재 이 환경에서는 Ethereum RPC 실측 호출에 성공하지 못했다.** 실측이라고 주장할 수 없도록 데이터 출처·파일명·화면에 표시했다.

## 0. 무엇을 만들었나

Ethereum의 **블록 헤더**를 읽고, 블록별 가스 사용률·EIP-1559 base fee·실행 계층 base-fee 소각 추정치·트랜잭션 해시 개수·간단한 이상치를 계산해서 오프라인 HTML 대시보드를 만드는 코드다.

가격 예측·스마트컨트랙트 거래·지갑 연결은 하지 않는다. 온체인 분석의 기초인 **수집, 데이터 품질, 단위 정합성, 출처 증명, 시계열 분석**을 코드로 보여준다.

## 1. 구조

| 파일 | 역할 |
|---|---|
| `observatory/rpc.py` | RPC `eth_chainId`, `eth_getBlockByNumber`, 연속 블록 무결성 확인 |
| `observatory/demo.py` | 검증 가능한 합성 블록 96개 생성. 실제 Ethereum 데이터 아님 |
| `observatory/analyze.py` | gas·base fee·소각 계산, 과거만 활용한 이상치 분류 |
| `observatory/dashboard.py` | 외부 라이브러리 없이 HTML·SVG 생성 |
| `observatory/main.py` | demo, live, report 명령 진입점 |
| `tests/test_observatory.py` | 체인 ID, 부모 해시 연결, 블록 범위, 미래 누수 방지 검증 |
| `artifacts/SYNTHETIC_demo_dashboard.html` | 지금 브라우저에서 바로 열 수 있는 시연 화면 |

## 2. 핵심 개념

- **블록:** 블록 번호, 부모 블록 해시, 타임스탬프, 가스 사용량, 트랜잭션 목록 등의 메타데이터를 갖는 체인의 단위.
- **블록 해시/부모 해시:** 연속 블록의 연결을 검증하는 식별자. 단, RPC 제공자가 신뢰 가능한지 별도 판단해야 한다.
- **RPC:** JSON-RPC 표준 형태로 실행 클라이언트에 정보를 요청하는 프로토콜. 이 코드에서는 읽기만 한다.
- **gasUsed:** 해당 블록에서 실제로 사용된 실행 가스 양.
- **gasLimit:** 해당 블록의 실행 가스 상한. 용량과 실제 사용량은 다르다.
- **baseFeePerGas:** EIP-1559의 프로토콜 단위 기본 수수료(wei/gas). 이 부분은 소각된다.
- **gwei:** 10억 wei. `baseFeePerGas / 1e9`로 환산한다.
- **ETH 소각:** EIP-1559 실행 가스 base fee 소각액은 `gasUsed * baseFeePerGas / 1e18` ETH. 총 소각액과 다르다.
- **MAD 이상치:** 중앙값으로부터 절대 편차 중앙값을 구해, 이상치에 강인한 척도를 만든다.

## 3. 실제 실행 방식

```bash
# ① 네트워크 전혀 사용하지 않는 모의 데모
python -m observatory.main demo
python -m pytest -q

# ② 인터넷 연결이 가능한 로컬에서 실제 mainnet (명시적 요청)
python -m observatory.main live --count 32 --end-tag finalized

# ③ 저장한 RPC 스냅샷을 네트워크 없이 재분석
python -m observatory.main report --input artifacts/last_live_rpc_snapshot.json
```

`live`는 `https://ethereum-rpc.publicnode.com`을 기본으로 사용하지만 네트워크·지역·공급자 상태에 따라 실패할 수 있다. 본 제작 환경에서는 실행을 검증하지 못했다. 개인 키·지갑은 필요 없고, 기밀 RPC URL을 공개 리포지토리에 커밋하면 안 된다.

## 4. 데이터 흐름

**입력:** Ethereum mainnet RPC 또는 명확한 SYNTHETIC JSON → **검증:** 필수 필드·정수형 단위·연속 번호·부모 해시·체인 ID(실측 모드만) → **연산:** 수수료·utilization·이상치 → **출력:** CSV + JSON + 독립형 HTML.

96개 블록을 시뮬레이션한 데모에서는 평균 gas utilization 약 59.1%, base fee 평균 약 71.66 gwei, 실행 base-fee 소각 합계 약 118.89 ETH로 나온다. **이 수치는 전부 합성 데이터 계산 결과이며 실제 2026년 Ethereum 상태와 무관하다.**

## 5. 이상치 로직의 역할과 한계

현재 블록 t의 사용률을 과거 12개 블록의 중앙값과 비교한다. `z=(u_t - median(u_history)) / max(1.4826×MAD, 0.05)`이고 `z>3`이면 표시한다. 현재 블록을 기준치 계산에 포함하지 않으므로 미래 누수를 피한다. 데이터가 12개 미만이면 이상치라고 확정하지 않는다.

이는 학습한 탐지 모델도 아니고, 서비스 장애나 보안 공격의 증거도 아니다. 데이터가 96개인 합성 예제에서 실제 이상치가 0개인 것도 정상적인 결과다.

## 6. 실무로 확장하려면

가장 직접적인 후속은 `eth_getLogs`로 검증된 ERC-20 토큰의 Transfer 이벤트를 수집하는 일이다. 재조직(reorg), RPC 다중화, 컨트랙트 주소·ABI·토큰 decimals, 잔고 변화 vs 이벤트, 페이지네이션, 영속 DB, 메서드별 한도, 최종 확인된 블록 경계를 추가해야 한다.

**이더리움 블록 단위 메트릭을 DeFi 생태계 전체의 사용자·거래량·유동성 지표라고 부르면 안 된다.**

## 7. 면접 예상 질문·모범답변 20개

### Q01. 이것은 온체인 분석인가?

**A.** 블록체인 실행 계층 블록 헤더를 실제 RPC로 읽도록 설계된 분석기다. 다만 현재 제공하는 실행 증거는 합성 데이터만이며 프로토콜 이벤트 단위의 온체인 분석까지 구현하지 않았다.

### Q02. JSON-RPC에서 eth_getBlockByNumber는 무엇을 받나?

**A.** 블록 번호를 hex quantity 또는 latest/safe/finalized 태그로 받고, 거래 내역을 해시 목록으로 받을지 객체 전체로 받을지 boolean으로 정한다.

### Q03. 왜 false로 거래 내역을 요청하나?

**A.** 개별 거래의 상세 필드 없이 트랜잭션 개수만 필요하므로 블록 헤더·해시 목록을 받아 응답 부하와 데이터 사용량을 줄인다.

### Q04. Ethereum mainnet을 어떻게 확인하나?

**A.** live 모드에서 `eth_chainId` 결과가 `0x1`인지 확인한다. 이 방법은 잘못된 체인 설정을 줄이지만, 악의적 RPC 제공자의 모든 행위를 검증하지는 못한다.

### Q05. 왜 finalized 태그를 기본값으로 쓰나?

**A.** 최종 확정 이후 재조직 위험을 낮추기 위해서다. 다만 제공자 지원 여부가 다르고, 수집 전에 최종 블록 확인 및 공급자 장애를 처리해야 한다.

### Q06. 부모 해시 검사는 무엇을 검증하나?

**A.** 연속 블록의 `parentHash`가 앞 블록의 `hash`와 일치하는지, 블록 번호가 1씩 증가하는지 검증한다. 이는 연속성 체크이며 암호학적 전 체인 검증은 아니다.

### Q07. EIP-1559 base fee의 역할은?

**A.** 가스 수요에 맞춰 프로토콜이 조정하는 기본 수수료이며 실행 가스를 사용한 부분의 base fee는 소각된다. 검증자 팁과는 구분된다.

### Q08. gasUsed/gasLimit은 무엇을 뜻하나?

**A.** 블록 실행 가스 상한 대비 실제 실행 가스가 사용된 비율이다. 데이터 샘플링과 네트워크 프로토콜 변화에 따라 의미를 추가 점검해야 한다.

### Q09. base fee가 10 gwei이고 gasUsed가 15M이면?

**A.** 10×10^9 wei/gas × 15×10^6 gas / 10^18 = 0.15 ETH가 실행 base fee로 소각된다는 계산이다.

### Q10. 계산한 burn이 Ethereum 총 소각량인가?

**A.** 아니다. EIP-4844 이후 blob 가스 base fee 소각 등은 별도이며, 본 코드는 실행 가스의 base fee 소각만 합산한다.

### Q11. Transaction count가 활성 사용자 수인가?

**A.** 아니다. 하나의 사용자가 여러 트랜잭션을 낼 수 있고 컨트랙트 호출은 내부 작업을 만들 수 있다. tx count만으로 고유 사용자 수를 측정할 수 없다.

### Q12. 소액 전송량이나 DeFi TVL도 볼 수 있나?

**A.** 이 프로젝트에서는 볼 수 없다. 이벤트 로그·토큰 단위, 컨트랙트 상태, 외부 가격·기준 통화 정규화 등이 별도로 필요하다.

### Q13. 왜 MAD를 쓰나?

**A.** 이상값에 표준편차보다 덜 흔들리는 강건 척도를 만들기 위해서다. 하지만 창 길이, floor, 임계값은 경험적 설정으로 검증이 필요하다.

### Q14. 미래 누수를 어떻게 차단했나?

**A.** 블록 t의 이상치 기준값은 이미 처리된 이전 12개의 gas utilization만으로 구한다. 마지막 블록 값을 변경해도 앞 블록 점수가 바뀌지 않는 테스트를 넣었다.

### Q15. RPC가 거짓 데이터를 돌려주면?

**A.** 다른 독립 공급자의 동일 블록 해시를 비교하거나 자체 노드·검증된 체크포인트 등을 이용해야 한다. 이 코드의 단일 RPC와 부모 해시 체크만으로 완전히 방지할 수 없다.

### Q16. reorg가 일어나면 데이터 엔지니어링은 어떻게 하나?

**A.** 확정되지 않은 구간의 블록 해시가 바뀔 수 있으므로 블록 번호뿐 아니라 hash/parentHash를 저장하고, 재조직 발생 시 영향 범위를 되돌려 재수집하는 설계를 한다.

### Q17. 왜 API 키 없는 공개 RPC를 선택했나?

**A.** 입문자가 데이터 수집 메커니즘을 직접 확인할 수 있게 하려는 목적이다. 공개 RPC는 정책·지역·부하로 차단될 수 있어 실서비스에는 다중 공급자·재시도·모니터링이 필요하다.

### Q18. 표시 화면의 synthetic 배지는 왜 중요한가?

**A.** 합성 값이 실제 체인 지표로 오해되면 잘못된 연구 결론을 낼 수 있다. JSON 데이터 provenance, 파일명, HTML 화면에 동시에 표시해 오용 가능성을 줄였다.

### Q19. 보안 관점에서 가장 먼저 할 개선은?

**A.** RPC URL에 포함될 수 있는 비밀 토큰의 로깅·커밋 차단, 요청 예산/타임아웃, 데이터 크기 제한, 응답 스키마 검증과 재시도 정책을 개선하겠다.

### Q20. 프론티어 수준의 후속 연구 한 가지는?

**A.** 검증된 DeFi 컨트랙트의 이벤트를 블록 단위로 재생하며 reorg-safe 파이프라인을 만들고, 독립 데이터 소스와 reconciliation 차트를 출력하는 것이다. 현재 버전에는 없다.
